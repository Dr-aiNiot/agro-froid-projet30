## BLOC 1 - Accroche (0:00 - 0:11)

"Ma partie, c'est l'étape finale du projet AGRO-FROID : transformer un
incident de chaîne du froid en une décision opposable, et la mettre entre
les mains d'un humain."

## BLOC 2 - Architecture (0:11 - 0:36)

"Le workflow tourne sur Agentic AI de ABA : cinq nœuds, quatre liens,
zéro modèle de langage, zéro clé d'API, zéro euro par décision.
C'est un choix délibéré : un rappel alimentaire ne peut pas être inventé
par un modèle de langage. Quatre décisions possibles, les quatre prouvées
au run : retrait, rappel, quarantaine, et escalade."

## BLOC 3 - Moteur (0:36 - 1:04)

"Comment ? Le moteur vérifie chaque ligne de télémétrie signée.
Un journal falsifié part en quarantaine, et il ne réduit jamais la
décision. Il recalcule les écarts par chambre : delta et durée.
Il applique la politique P1 à P6, et il sort un schéma canonique de
neuf clés, validé à chaque exécution. Si une clé manque, rien ne sort."

## BLOC 4 - HITL (1:04 - 1:27)

"Une fois la décision armée, quatre décisions sur cinq déclenchent une
porte d'approbation humaine. Le token est signé, à usage unique, et
expire en trente minutes. Rejouer le token est refusé.
Le rappel exige en plus un double contrôle.
En un mot : l'agent prépare, l'humain signe."

## BLOC 5 - Preuves (1:27 - 1:45)

"Résultat mesuré : quarante-deux tests qui passent, dont dix-huit cas
limites. Quatre décisions prouvées au run sur la plateforme.
Et si la livraison échoue, une file morte conserve l'événement signé,
et le rejeu se fait sans re-décision : aucun doublon."

## BLOC 6 - Test en direct (1:45 - 2:06)

"Maintenant, le test en direct. Je rejoue les quatre cas sur le flux
M5 B4 : nominal, rappel, quarantaine, escalade.
Chaque cas sort le même contrat : neuf clés, schéma validé,
HITL requis, et aucun modèle de langage dans la boucle."

## BLOC 7 - Cloture (2:06 - 2:28)

"Enfin, la batterie de tests : quarante-deux tests, tous verts, en moins
d'une seconde. La décision de départ est reproductible, et la supervision
humaine est en place. Voilà pour ma partie. Passons à l'orchestration
complète."

## MISE A JOUR 07/11 - WORKFLOW UNIQUE (2 passages)

Un seul workflow : `M5_B4_DECISION_HITL`, 6 noeuds / 5 liens, avec un noeud FusionDB (MongoDBQuery) cable
entre le Parseur et la Sortie. Pas de LLM, aucune cle API.

Tour 1 - dire : "Je lance le cas rappel."
Resultat attendu : decision RAPPEL, motif P2_LOT_VENDU, schema 9/9, puis
"APPROBATION REQUISE - repondre dans le meme chat : APPROVE pending_id=MFP-... actor=VOTRE_NOM".

Tour 2 - dire : "Le dossier est en attente. J'approuve."
Saisir : APPROVE pending_id=MFP-... actor=VOTRE_NOM
Resultat attendu : type APPROVAL, verdict APPROVE, statut DONE, token_verifie true, inserted_id.
Phrase de cloture : "L'agent prepare, l'humain signe : le journal est append-only, rien n'est ecrase."

Si le jury demande "ou est le blocage ?" : "Le flux s'arrete sur la demande d'approbation, ecrite en base
avec son identifiant. Le second message, dans la meme session, reprend ce dossier et l'approuve."

## PROTOCOLE REEL VALIDE LE 07/11 (a suivre a la lettre)

Contrainte technique du fork : le noeud FusionDB ferme son client Mongo apres
chaque execution. Un deuxieme run dans le MEME graphe sans rechargement echoue
avec "Cannot use MongoClient after close". Donc :

1. Ouvrir le workflow M5_B4_DECISION_HITL (6 noeuds / 5 liens, nœud FusionDB cable).
2. Playground -> saisir `rappel` -> attendre la reponse.
   Sortie attendue : RAPPEL, P2_LOT_VENDU, schema 9/9, puis
   "type": "PENDING_DOSSIER", "statut": "PENDING", pending_id MFP-...,
   instruction "APPROBATION REQUISE - repondre : APPROVE pending_id=... actor=...",
   et "inserted_id". Le flux s'arrete la.
3. FERMER / RECHARGER le playground (ou la page) : le client Mongo est recree.
4. Playground -> saisir `APPROVE pending_id=<celui affiche> actor=VOTRE_NOM`.
   Sortie attendue : "type": "APPROVAL", "verdict": "APPROVE", "statut": "DONE",
   token_verifie true, inserted_id.
5. Phrase de cloture : "Journal append-only : l'agent prepare, l'humain signe,
   rien n'est ecrase. La preuve est en base."

Si on demande "pourquoi recharger ?" : "le connecteur Mongo de la plateforme
ferme son client apres chaque appel ; en production on garderait une connexion
pool, ici on relance la session pour le deuxieme passage."

Preuves disponibles dans la video Demo_M5_Complet.mp4 (3 min 24) :
canvas 6 nœuds, tour 1, tour 2, verification Mongo (7 documents), CI GitHub verte.
